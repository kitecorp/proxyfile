# Conformance

The conformance battery runs a proxy on the configuration proxyfile renders for it and checks that the proxy answers
requests as the proxyfile says. It is the Go package [`conformance`](../conformance), whose files are test files only,
so the released program never carries them. It runs each target of this version: Envoy on Envoy 1.40.2, nginx on nginx
1.30.6 and 1.31.8, each on its plain image and on its image tagged `-otel`, and HAProxy on HAProxy 3.2.26 and 3.4.7.

## What the battery proves

Each entry of the battery is a proxy image and the proxyfiles it runs. Envoy's entry, `envoy-1.40`, runs eleven:
[`examples/full/hocon/Proxyfile`](../examples/full/hocon/Proxyfile), which writes every key but the few its opening
comment names, [`examples/portable/hocon/Proxyfile`](../examples/portable/hocon/Proxyfile), which writes in the same
world only the keys every generator is to render alike, nginx's own seven files,
[`conformance/testdata/nginx.yaml`](../conformance/testdata/nginx.yaml) and
[`conformance/testdata/nginx-plain.yaml`](../conformance/testdata/nginx-plain.yaml), the same with no pattern route, and,
with an auth check, [`conformance/testdata/nginx-checks.yaml`](../conformance/testdata/nginx-checks.yaml) and
[`conformance/testdata/nginx-auth.yaml`](../conformance/testdata/nginx-auth.yaml), and, with tracing,
[`conformance/testdata/nginx-tracing.yaml`](../conformance/testdata/nginx-tracing.yaml) and
[`conformance/testdata/nginx-tracing-by-name.yaml`](../conformance/testdata/nginx-tracing-by-name.yaml), its collector
found by name, and, with a connection limit,
[`conformance/testdata/nginx-limits.yaml`](../conformance/testdata/nginx-limits.yaml),
and HAProxy's own two, [`conformance/testdata/haproxy.yaml`](../conformance/testdata/haproxy.yaml) and
[`conformance/testdata/two-checks.yaml`](../conformance/testdata/two-checks.yaml).
The nginx entries `nginx-1.30` and `nginx-1.31` run on the two images pinned in `scripts/nginx-images`, one entry for
each line, and run nginx's own files but the two with tracing, `examples/full`, which nginx refuses, and
`examples/portable`. The nginx entries `nginx-otel-1.30` and `nginx-otel-1.31` run on the two images pinned in
`scripts/nginx-otel-images`, the same nginx versions in the images tagged `-otel`, which carry nginx's OpenTelemetry
module, one entry for each line, and run the two files with tracing alone: a file with `tracing` loads that module,
which the plain images do not carry ([nginx](nginx.md#tracing)). Each line of `scripts/nginx-otel-images` names an image
tagged `-otel` and each line of the other files names one that is not, pinned by digest, as
`nginx:<major>.<minor>.<patch>-otel@sha256:<digest>` or the same without `-otel`; the battery stops before any container
at a line that does not, and `scripts/pinned-images.sh` takes no image from such a file.
The HAProxy entries, `haproxy-3.2` and `haproxy-3.4`, run on the two images pinned in `scripts/haproxy-images`, one
entry for each line, and run HAProxy's own two files and `examples/full` and `examples/portable`, which HAProxy refuses. Each
file is rendered for the entry's target with `proxyfile render --target <name>` through the program's own command line,
the path a user takes. The proxy then runs on the rendered file in its own image, among stub backends, and the same
requests get the answers the format promises.

`conformance/testdata/<proxy>.yaml` is a proxy's own file, and `<proxy>-<name>.yaml` another of its own: the world of
`examples/full`, or of `examples/portable` for HAProxy, with only the keys that proxy's generator writes in this
version, so the rows whose keys it writes run on that proxy before its generator writes every key. Envoy's entry runs it
too, so its answers are Envoy's, measured as every other answer is. nginx's `nginx.yaml` writes `tls` with `clients`,
`client_address: connection`, `remove_from_clients`, `cors` and the lists of every environment as `examples/full` does,
but `remove_from_clients` names only `x-client-id`, because the generator refuses a name with a `*` prefix. It also
writes `limits: {request_headers: {size: 60KiB, count: 100}}`, Envoy's own defaults; `timeouts: {idle: 2s,
upstream_idle: 3s}`, an idle time short enough that a row sees a silent service ended without waiting long; and `log:
{status_from: 400, sample: 1%}`, `examples/full`'s, so the battery runs every form of those keys the generator writes.
Its traffic keys are `examples/full`'s: `catalog` found by its DNS name through `dns: {resolver: "10.0.0.2:53"}` and
balanced by the hash of `x-session-id`, the catalog route limited to 20 requests a second with a burst of 10 by client,
the rpc entry's `retries: 1` and its limit of 100 a second for all, and `shop` balanced by `least_requests`; but the
shop route writes `retries: 0`, which tries each of its requests once, so the rows that send it a body meet the form
nginx streams, and two routes of their own to shop write `retries: 1`, `/retried/` and `/retried-limited/`, the second
limited to 10 requests a minute for all, which the rows that need a retry send to; and a service `sessions` at shop's
two addresses, balanced by the hash of `x-session-id`, takes the route `/sessions/`, which no limit holds, so the hash
rows send to a route the rate limit rows do not spend. `nginx-plain.yaml` writes no `tls`, keeps `client_address` at
`forwarded`, the default with no `tls`, and removes `x-request-id` from clients, which nginx reads to keep a client's
own request id under `forwarded`. It writes none of `limits`, `timeouts` and `log`, so it runs each proxy's defaults,
and it names the service `hold`, at `10.0.2.30` on port 8095, behind the route `/hold/`, and the service `held`, at

A file that writes no `tls` is sent over plain HTTP: HTTP/1.1, and HTTP/2 with prior knowledge. A file with `tls` is
sent over TLS, with a client certificate the run's clients CA signed ([The world](#the-world)). Every request goes to
the proxy's one listener, and the client asks for the host the request names as its TLS server name, without the port,
as a browser does, and checks the server certificate against `localhost`, the name it carries; an empty host, a host
that is an IP address, and one that holds a character other than a letter, a digit, a dot or a hyphen ask for
`localhost`. A row may name a server name of its own. nginx answers `421` to a request whose `Host` is another name than
its TLS server name when it asks for client certificates, so a client that asked for one name whatever the host a row
sends would read that refusal in every row that names another host.

origins file a proxyfile names and of the methods its `rpc.proto` reads; a row that names none runs on every file.

the headers a client may not send it (`x-client-id`, `x-user-id` and the mark) and of a client's `HTTP2-Settings`;
`allow-empty` allows with no header, so a row sees that the service receives none of an earlier answer's; and
`redirect-relative` answers `302` with a `Location` that is a path, `/login?next=%2Fx`. `deny-401-empty` answers `401` with no body; `chunk-size-lf`, `last-chunk-lf` and `chunk-other-lf` write a bare LF at the end of a chunk-size line, of the last chunk's line and of a chunk's data, a trailer line and the final line; `folded-tab`, `folded-spaces` and `folded-twice` allow with an `x-user-check` that the check folds onto a second line; `accept-past-size` allows with an `x-user-check` of 70,000 bytes, `accept-60000` with one of 60,000 bytes, and `accept-empty` with one that is empty. Thirty-three more tokens write a
raw answer for the forms nginx's reader of an answer reads in a way of its own, a status line, a header line or a framing
that RFC 9112 does not admit, a `304`, a `500`, a `503` with a body, a `599` and a `101`, a header name `x-proxyfile-check`, a denial's
header that holds the byte `0xE9`, and bodies of 1 MiB, of one byte more and of 1,100,000 bytes; each `200` of them reports its token in `x-user-check`, so a
row reads back that it was allowed.
A backend answers with `X-Accel-Redirect` set to the value of the request's `x-stub-accel-redirect`, on HTTP and gRPC,
so a row can check that the proxy passes the header on instead of following it, and with `Keep-Alive` set to the value
of `x-stub-keep-alive`, so a row can check that the proxy removes it, and with as many bytes more as
`x-stub-pad` asks for, so a row gets an answer of 100 KB. A request the stub cannot read gets
the stub's own answer, the plain-text status line of Go's `net/http`, and no description of the request: a row that
wants that answer says `unreadable`, and a row that wants no service fails on it.
A backend holds its answer for the time `x-stub-delay` names, such as `3s`, and with `x-stub-trickle: <n>x<time>`, such
as `2x1250ms`, sends the status and the headers at once, then a space after each of n pauses of that time, then its
echo, a space being nothing to the JSON the client reads: a row sees a service silent past a proxy's idle time, and one
that keeps sending within it. A backend stops waiting when the proxy closes the request.
The backends share the volume `proxyfile-conformance-state`: a request the stub closes on its first
try is answered by whichever backend a second try reaches, so a retry would show. A backend refuses connections, as
one that is down does, while a row needs it to: the battery sends its container `SIGUSR1`, which closes every port
and connection of the stub, and waits until a connection made inside the container is refused; after the row,
`SIGUSR2` opens the ports again, and the battery waits until each answers. The stub is built with Go for the platform
the Docker server runs and copied alone into the image `proxyfile-conformance-stub`.

Before the first request, the stub in `accounts`, which shares the proxy's network namespace, fetches the target's
ready URL every 100 ms until it answers 200, for 30 s at most: the proxy's admin listener answers only on `127.0.0.1`,
and Envoy's image has no shell.

Each run makes throwaway TLS files: a self-signed server certificate for `localhost` and `127.0.0.1` with its key, a
clients CA, and a copy of the server certificate as the CA bundle `examples/full`'s `auth.jwt.ca` names. They are
written to the folder `proxyfile-conformance` in the system's temporary folder (`$TMPDIR`, or `/tmp`), with the
rendered file and the stub's build, and the folder is the user's alone; the proxy reads its `tls` and `jwt` folders
through their own mounts. The three client certificates, one the clients CA signs, one a second CA of the same name
signs, and one the clients CA signed whose validity ended a day before the run, stay in memory with their keys, so the proxy never sees them and no run writes them to disk.

## What it does not prove

- Answers each proxy writes in its own words. No row checks a local reply's body, or that an answer carries a header a
  proxy names after itself, which [portability](portability.md) classes as that proxy's own: measured on Envoy 1.40.2,
  the `403` body `Invalid CORS request`, the empty `502`, the `429` body `local_rate_limited`, and the `403` Envoy
  answers when the check answers `204`. A row may check such a header absent, which holds for every proxy, as the two
  denial rows do. The mark of a request the check could not answer, `x-envoy-auth-failure-mode-allowed`, is checked
  although it carries Envoy's name, because every proxy writes that name.
- A retry of a service with one backend. A row would need the backend to refuse exactly one connection and accept the
  next, which the stub cannot time. Measured on Envoy 1.40.2 instead, with a firewall rule in the backend's own network
  namespace that refused one connection: the retry went to the same backend and was answered `200`, five times of
  five.
- Keys no scenario names. The rendered file carries them, and the proxy loads it, but no row checks what they do:
  among others `auth.jwt` but its `claims`, `timeouts.request` and `timeouts.upstream_idle`.
  No row sends a valid token, so of `auth.jwt.claims` only the removal of a client's own copy is checked. The table
  above names every key a scenario exercises.
- Spaces and tabs around a header value over HTTP/1.1. Envoy removes them and nginx passes a tab on, as
  [nginx](nginx.md#what-nginx-writes-with-no-key) says, but no row shows it: the stub reads each header through Go's
  `net/http`, which removes the spaces and tabs around a value before the stub reports it, so a service behind
  every proxy reports the same value.
- What the check is told of the host beyond `Host`. The stub's check reports the method and the path the proxy told it,
  and for one token the `Host` and `x-forwarded-proto` it received, not `x-forwarded-host`.

## Running it

It needs Docker and Go. From the repository root:

```sh
go test -tags conformance -count=1 -timeout 30m ./conformance/...
```

`-timeout 30m` gives a whole run, which comes close to `go test`'s default of 10 minutes, room to finish, and a run
started while another holds the battery's lock room to wait for it (below).

The battery's tests are behind the build tag `conformance`, so `go test ./...` without it starts no container. Each
row is a subtest, `TestBattery/<entry>/<file>/<scenario>/<row>` with `_` for each space, which `-v` lists, so
`-run 'TestBattery/envoy-1.40/portable/routing'` runs one scenario on one file. A row that fails prints each way its
answer differs, for example `service: got "shop", want "catalog"`, and the proxy's last 50 log lines follow.

The first run pulls the proxy's image by the digest in [`scripts/envoy-image`](../scripts/envoy-image), the file
[`scripts/validate-envoy.sh`](../scripts/validate-envoy.sh) also reads, so an Envoy upgrade changes one line for both;
it pulls nginx's two images by the digests in `scripts/nginx-images` and its two images tagged `-otel` by those in
`scripts/nginx-otel-images`, which [`scripts/validate-nginx.sh`](../scripts/validate-nginx.sh) reads in the same way,
and HAProxy's two by the digests in `scripts/haproxy-images`, which HAProxy's validator, `scripts/validate-haproxy.sh`,
reads. With the images already pulled and a warm Go build cache, thirty runs of every entry's files, twenty-two worlds
in all (one for each file of each entry that starts a proxy: eight in Envoy's entry, five in each nginx entry and two in
each HAProxy entry), passed on one arm64 Mac, with Docker giving its containers 12 CPUs, and none waited for another
run's lock. The runs came one after the other. Runs 11, 12 and 13 started on battery power and run 10 may have ended on
it, and other work on this project, Go builds and unit tests with no container, ran on the same Mac from the end of run
10 to the end of run 21, so every time and every memory figure here is that of the eighteen runs, 1 to 9 and 22 to 30,

test` times a run. Other programs used the machine during the runs: two containers of another program ran beside every

The battery removes its own leftovers when it starts and everything it made when it ends but its lock (below): the
containers named `proxyfile-conformance-<role>`, the network `proxyfile-conformance`, the volume
`proxyfile-conformance-state`, the image `proxyfile-conformance-stub` and the folder `proxyfile-conformance` in the
temporary folder. It touches no other Docker object. A run stopped before its end, by `go test`'s `-timeout` or an
interrupt, leaves all of them: the containers keep running, the proxy still published on `127.0.0.1`, and the folder
keeps the run's server key, made for that run alone and trusted by nothing else. The next run removes them when it
starts; to remove them at once:

```sh
docker rm -f proxyfile-conformance-accounts proxyfile-conformance-proxy proxyfile-conformance-shop-1 \
  proxyfile-conformance-shop-2 proxyfile-conformance-catalog proxyfile-conformance-check-1 \
  proxyfile-conformance-check-2 proxyfile-conformance-resolver
docker network rm proxyfile-conformance
docker volume rm proxyfile-conformance-state
docker image rm proxyfile-conformance-stub
rm -rf "${TMPDIR:-/tmp}/proxyfile-conformance"
```

The names are fixed, so a run takes a lock, an exclusive `flock` on `/tmp/proxyfile-conformance.lock`, before its first
file touches Docker, and gives it back once, after it removed what it made for its last file. The path is the same
whatever `TMPDIR` is, so two runs on one machine take turns, from two checkouts, two users or two jobs. A run that finds
the lock held logs that it waits, and waits once: until `go test`'s `-timeout` would leave under 12 minutes for its
worlds after the wait, because that timeout ends the run without removing them, or with `-timeout 0` as long as the lock
is held; then it stops and says another run holds the lock. With the command's `-timeout 30m` a run waits out a first
run that ends within 18 minutes; under `go test`'s default of 10 minutes it waits for none. A run of the checks alone,
such as `-run 'TestBattery/none'`, takes no lock. The file stays, so every run locks the same one. A killed run holds no
lock, because the kernel gives it back, and the next run removes the Docker objects the killed one left. The lock does
not reach past the machine's own `/tmp`: runs that share a Docker daemon from two machines, or from a container that
uses the host's daemon, do not see each other's lock and still remove each other's containers, as does a battery older
than the lock. When another network already holds addresses in `10.0.0.0/22`, the run stops with Docker's `Pool
overlaps` answer and says which range it needs; it removes no network it did not make, so free the range or run on
another Docker host.

The check `Required` of the `Pre-merge` workflow runs `go vet -tags conformance ./conformance/...` and the battery after
the Envoy, nginx and HAProxy validations, whose pulls leave the images cached. The release workflow runs the battery
before it builds the release, so a release whose rendered configuration answers a scenario otherwise than the format
says is not published.

## Adding a proxy

A proxy joins in four places, and a row changes for it only where it declares a difference that changes the row's
answer (`by`, above):

1. Its generator in `render.Targets` in [`internal/render/render.go`](../internal/render/render.go): the `--target`
   name, the configuration's file name and the function. `render` and the command line read the targets there.
2. Its declaration of every core key and of the two behaviours written with no key, in a file of its own in
   [`internal/format`](../internal/format), listed in `format.Targets` in
   [`internal/format/support.go`](../internal/format/support.go). A key it does not write yet is declared refused, and
   a form of a key it refuses, by the key's value or for want of another key, is a `Refuses` entry of that key, which
   it declares partial.
3. `go test ./internal/render -run TestExamplesAreCurrent -update` writes each example's configuration for it, or
   `<proxy>.refused` where it refuses a key the example writes, and `go test ./internal/format -update` writes its
   column of the support table.
4. An entry per image, made in a file of its own, `conformance/targets_<proxy>_test.go`, by a function `targets` in
   [`conformance/targets_test.go`](../conformance/targets_test.go) calls: its label, the `--target` name, the files it
   runs, the header it adds to a request the check could not answer, its image pinned by digest, its arguments and
   the URL that answers 200 when it is ready. Its images are in `scripts/<proxy>-images`, one a line, tagged with its
   version and pinned by digest, read by its entries through `pinnedImages`, which labels each `<proxy>-<major>.<minor>`,
   and by its validator, `scripts/validate-<proxy>.sh`, which `Required` runs on every configuration the examples commit
   for it. The rendered files are mounted in `/config`, the
   configuration at `/config/<file name>`, and the ports 10000 and 9901 and the folders `/etc/gateway/tls` and `/etc/gateway/jwt` are
   the examples', the same for every target. The files of its entries of one version together must run each row
   Envoy's files run, unless its target refuses one of the row's keys, or the battery fails before any container
   starts: an image that loads only some files, as nginx's images tagged `-otel` load the tracing module, runs them in
   an entry of its own, which is judged with the other entries of the same version.

## The documentation site

The README and the pages under `docs/` are also published as a site, at https://kitecorp.github.io/proxyfile/, built
from the same files, so no page is written twice. That address is the line `baseURL` in
[`site/hugo.toml`](../site/hugo.toml), the one line to change when the site is served at another.
[`scripts/build-site.sh`](../scripts/build-site.sh) builds it with Hugo, the release pinned by digest in
`scripts/hugo-image`, from the configuration in [`site/`](../site). Each page keeps its file's place and name, capitals
included, `docs/<name>.md` as `docs/<name>.html` and the README as the first page, `index.html`. A link between pages
leads to the built page and its heading, a link to any other file of the repository leads to that file on GitHub at the
commit built, and the build fails on a link to a file the repository does not hold. A page of four sections and
subsections or more starts with the list of them. Each page names, for search engines and link previews, a description
taken from its first paragraph, its one canonical address and its Open Graph title, description, type and address;
`sitemap.xml` lists every page, and `robots.txt` names the sitemap. The README's own Made by section is the credit on
the first page, and the footer of every other page renders it.

A Mermaid block, in a list or a quote too, is drawn as on GitHub, by a copy of Mermaid the build fetches at the release
pinned in `site/hugo.toml`, from jsDelivr or, when jsDelivr does not answer, from unpkg, and refuses unless its SHA-256
sum is the one pinned there. The site serves that copy itself, and a page with a diagram asks for it only when a
diagram comes near the screen. Until then the diagram's box keeps its place, and a reader without scripts sees the
block as code. A wide diagram is drawn at its own size and scrolls in its box.

The build refuses a page that the site would show otherwise than GitHub, naming the page and the text. Before Hugo
runs, it refuses a page that holds two opening braces followed by `<` or `%`, which Hugo reads as the start of its own
shortcode anywhere in a page, in a code block too, and a page whose first text starts with `-`, `+`, `{` or `#+`, which
Hugo reads as front matter. Hugo then refuses a page whose Markdown writes a script, an `on...` attribute such as
`onload`, a frame, an object, an embed or a `base` element: GitHub never runs a script a page writes, and the site
would.

[`scripts/check-site.sh`](../scripts/check-site.sh) then reads what was built, every tag as a browser reads it, in any
quoting or case and outside comments. It fails when a page `git ls-files 'docs/*.md'` lists has no built page, when a
footer is not the first page's Made by paragraph byte for byte or a page says it twice, when a Mermaid block is not
drawn, when a page lacks its description, canonical address or Open Graph names or the sitemap does not list it once,
when a page of four sections or more does not start with their list, when a page holds a script the theme did not
write, a frame or a `base` element, when the browser would fetch from another host something the page's own Markdown
does not name, or when a link leads to no built file or names no heading of it. A link that leaves the site is checked
for its form, never fetched.

The check `Required` builds and checks the site without publishing it, so a change that breaks a page or a link fails
before it merges. The `Pages` workflow builds and checks it the same way on each push to `master`, or when started by
hand, and publishes it when it runs on `master`. To build and check it yourself, with Docker running:

```sh
site=$(mktemp -d)
scripts/build-site.sh "$site" && scripts/check-site.sh "$site"
```
